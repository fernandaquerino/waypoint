# ADR-004: Authentication with Auth.js, Drizzle and NestJS

**Status:** accepted  
**Date:** 2026-07-07  
**Context:** define login, session and identity validation across Next.js + NestJS + PostgreSQL.

## Context

Waypoint needs real login from Sprint 0 on, so that every future entity is born isolated per user. The product architecture uses Next.js as the web/BFF layer, NestJS as the business-rules API and PostgreSQL as the primary database.

Requirements for this decision:

- login with Google;
- login and sign up with email/password;
- password stored only as a hash;
- persistent session in an httpOnly cookie managed by Auth.js;
- JWT validated by NestJS on protected routes;
- `userId` always derived from the session/token, never from the client.

## Decision

We will use **Auth.js in Next.js** as the authentication authority and **NestJS validating a signed JWT** on protected routes.

Auth.js runs on the Next.js App Router with:

- the Google provider;
- the Credentials provider for email/password;
- `@auth/drizzle-adapter` using the Drizzle schemas from `@waypoint/db`;
- a `jwt` session strategy;
- custom encode/decode in JWS HS256 so NestJS can validate offline.

NestJS exposes credential endpoints and one protected route:

- `POST /auth/register`;
- `POST /auth/login`;
- `GET /auth/me`.

The `GET /auth/me` endpoint uses a JWT guard and returns only the `userId` extracted from the validated token.

## Shared Secret

The decision is to use **only `AUTH_SECRET`** as the shared secret.

`AUTH_SECRET`:

- signs the JWT in Auth.js;
- validates the JWT in NestJS;
- must be the same value for web and API;
- removes the need for a separate `JWT_SECRET` at this stage.

Local variables:

```env
AUTH_SECRET=
AUTH_URL=http://localhost:3000
API_URL=http://localhost:3333
WEB_URL=http://localhost:3000
DATABASE_URL=postgresql://waypoint:waypoint@localhost:5432/waypoint
GOOGLE_CLIENT_ID=
GOOGLE_CLIENT_SECRET=
```

## Persistence

The authentication schema lives in `packages/db`:

- `users`: base user, unique email, image, timestamps, nullable `password_hash` and `email_verified`;
- `accounts`: OAuth link used by Auth.js for Google.

`password_hash` is nullable because users created through Google don't need a local password.

## Flows

Sign up by email/password:

1. Next.js calls `POST /auth/register`.
2. NestJS normalizes the email, generates a hash with bcrypt and persists it through Drizzle.
3. Next.js calls `signIn("credentials")`.
4. Auth.js issues a session cookie with a signed JWT.

Login by email/password:

1. Auth.js Credentials calls `POST /auth/login`.
2. NestJS compares the password against the stored hash.
3. Auth.js issues the session/JWT when the user is valid.

Login with Google:

1. Auth.js runs the OAuth flow.
2. `@auth/drizzle-adapter` creates or reuses `users` and `accounts`.
3. Auth.js issues the session/JWT with `sub = users.id`.

Web -> protected API call:

1. Next.js reads the JWT from the httpOnly cookie on the server.
2. Next.js calls the API with `Authorization: Bearer <token>`.
3. NestJS validates the token with `AUTH_SECRET`.
4. Controllers use only `req.user.id`.

## Consequences

Positive:

- OAuth is handled by Auth.js, with no need to reimplement Google by hand.
- NestJS exercises and uses a real JWT guard.
- The browser does not store the token in `localStorage`.
- The backend validates identity without trusting a `userId` sent by the client.

Trade-offs:

- `AUTH_SECRET` must stay in sync between web and API.
- A signed JWT has no instant revocation before it expires.
- The custom HS256 format must be reviewed on major Auth.js upgrades.

## Out of this Decision

- password recovery;
- email verification;
- RBAC;
- 2FA;
- full account deletion.
