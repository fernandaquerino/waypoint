# ADR-003: Monorepo structure

**Status:** proposed
**Date:** 2026-07-07
**Context:** define how to organize backend, frontend and shared packages in the same repo

## Context

Waypoint has two apps (`apps/api` in NestJS and `apps/web` in Next.js) that share relevant code: Zod validation schemas, types derived from the Drizzle schema, and probably a minimal design system (`packages/ui`). Keeping this in separate repos means duplicating types, or publishing internal packages to a private registry. Neither is acceptable for a solo 2h/day project.

A monorepo has already been decided. The question now is **which tool manages the monorepo** and what internal structure to adopt.

## Options considered

### Option A: Plain pnpm workspaces

Just pnpm + `pnpm-workspace.yaml` + TypeScript project references. No extra layer.

**Pros:**

- Zero configuration beyond `pnpm-workspace.yaml`
- Real symlinks between packages via `workspace:*`, no publishing
- pnpm alone already handles dedupe, fast install, nested node_modules (more correct than hoisted)
- You learn **one** tool, not two stacked on top of each other
- No magic, everything transparent

**Cons:**

- No build cache. Run `pnpm build` in the monorepo and it recompiles everything
- No task graph (you orchestrate by hand via `pnpm -r` or `pnpm --filter`)
- No smart parallelization between dependent tasks

### Option B: Turborepo on top of pnpm workspaces

Adds `turbo.json` to orchestrate tasks, cache builds and parallelize. Owned by Vercel, integrates well with Next.js.

**Pros:**

- Local (and optional remote) build cache. Run the same `build` twice and the second is instant
- Automatic task graph: `turbo build` knows `apps/web` depends on `packages/ui` and builds them in the right order
- Parallelization between independent tasks
- `turbo dev` brings up all apps at once with one command

**Cons:**

- One more layer. You maintain `turbo.json` AND `pnpm-workspace.yaml`
- Configuring caching keys correctly takes care. A wrong cache creates phantom bugs
- Overhead that only pays off when builds get slow, which isn't your case in the first months

### Option C: Nx

A robust monorepo framework with generators, plugins, a visual dependency graph, distributed cache.

**Pros:**

- Best DX for a large monorepo. Commands like `nx g @nx/nest:app api` that generate a full structure
- Visual dependency graph
- Native distributed cache
- Strong official support for NestJS and Next.js

**Cons:**

- Strong opinions. It wants to manage everything its own way
- Steep curve. You learn Nx **before** you can write the first feature
- Built for large teams with many apps. You have two. And you'll keep having two
- Replaces NestJS's `nest g` with Nx generators, which works against the goal of learning plain NestJS

**Verdict:** overkill for the context. Noted as a reference in case the project grows into something with multiple apps.

## Decision

**Plain pnpm workspaces (Option A).**

Turborepo comes later **if and when** you feel real build pain. Nx is ruled out.

Reasons:

1. **You have two apps.** A task graph for two apps doesn't justify an orchestration tool. `pnpm -r --parallel dev` brings up backend and frontend together and solves it.

2. **You don't build in CI all the time.** A nightly side project doesn't pressure the pipeline. Turborepo's cache gains only show up when the build becomes a bottleneck, and while it's 2h/day on a small app, that's a long way off.

3. **One fewer tool to learn.** You're learning NestJS, Drizzle in a new context, NestJS + Next integration via JWT. Adding Turborepo now dilutes focus with no clear return.

4. **Migrating to Turborepo later is cheap.** Adding `turbo.json` and changing scripts to `turbo dev` instead of `pnpm dev` takes an hour. If it ever hurts, you fix it on a Saturday.

## Consequences

**Positive:**

- The Sprint 0 setup stays lighter. Less config, more code.
- Real symlinks between packages mean you change `packages/types` and `apps/api` sees the change immediately, with no manual rebuild.
- You learn monorepos through the fundamental path (workspaces + TypeScript project references), which is transferable knowledge.

**Negative:**

- If one day you add `packages/emails`, `packages/config`, `packages/scripts`, etc., manual orchestration starts to chafe. That's when it's time to look at Turborepo.
- Without incremental cache, CI runs all checks every time. Acceptable for the current volume.
- You set up Vercel manually if you deploy via Vercel (rootDirectory + buildCommand need to point to `apps/web` with monorepo context).

**Neutral:**

- pnpm requires an `.npmrc` with a few settings. Documented below.
- node_modules end up nested, which is more correct but occasionally confuses tools that assume hoisting (rare in 2026).

### `pnpm-workspace.yaml`

```yaml
packages:
  - "apps/*"
  - "packages/*"
```

### `.npmrc` at the root

```
link-workspace-packages=true
prefer-workspace-packages=true
save-workspace-protocol=rolling
strict-peer-dependencies=false
```

- `link-workspace-packages=true`: automatically links internal packages when an app declares the dependency
- `prefer-workspace-packages=true`: prefer the workspace version over the registry
- `save-workspace-protocol=rolling`: when you `pnpm add`, it saves as `workspace:*` (doesn't pin the version)
- `strict-peer-dependencies=false`: Next.js and some packages complain about peer deps without this override

### Root `package.json`

```json
{
  "name": "waypoint",
  "private": true,
  "packageManager": "pnpm@9.15.0",
  "scripts": {
    "dev": "pnpm -r --parallel dev",
    "build": "pnpm -r build",
    "lint": "pnpm -r lint",
    "typecheck": "pnpm -r typecheck",
    "test": "pnpm -r test",
    "db:generate": "pnpm --filter @waypoint/api db:generate",
    "db:migrate": "pnpm --filter @waypoint/api db:migrate",
    "db:studio": "pnpm --filter @waypoint/api db:studio"
  },
  "devDependencies": {
    "prettier": "^3.4.0",
    "typescript": "^5.7.0"
  }
}
```

`pnpm -r` runs the script in every package that defines it. `--parallel` runs them at the same time. `--filter @waypoint/api` runs it only in the named package.

### `packages/types/package.json`

```json
{
  "name": "@waypoint/types",
  "version": "0.0.0",
  "private": true,
  "main": "./src/index.ts",
  "types": "./src/index.ts",
  "scripts": {
    "typecheck": "tsc --noEmit",
    "lint": "eslint src"
  },
  "dependencies": {
    "zod": "^3.24.0"
  }
}
```

Note that `main` points to `.ts`, not `.js`. This works because both NestJS and Next.js compile TypeScript on the fly. You don't publish this package to a registry, it only exists internally. Zero build step for internal packages until you need one.

### `apps/api/package.json` (relevant excerpt)

```json
{
  "name": "@waypoint/api",
  "dependencies": {
    "@waypoint/types": "workspace:*",
    "@nestjs/core": "^10.4.0",
    "drizzle-orm": "^0.36.0",
    "pg": "^8.13.0",
    "zod": "^3.24.0"
  }
}
```

`workspace:*` says "take it from the workspace, any version". pnpm resolves it automatically to `packages/types`.

### `apps/web/package.json` (relevant excerpt)

```json
{
  "name": "@waypoint/web",
  "dependencies": {
    "@waypoint/types": "workspace:*",
    "@waypoint/ui": "workspace:*",
    "next": "^15.1.0",
    "react": "^19.0.0",
    "zod": "^3.24.0"
  }
}
```

### TypeScript project references

Each `tsconfig.json` points to the packages it consumes. This helps the IDE (VSCode) navigate correctly and helps tsc validate in order.

`apps/api/tsconfig.json`:

```json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "references": [{ "path": "../../packages/types" }],
  "include": ["src/**/*"]
}
```

`packages/types/tsconfig.json`:

```json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "composite": true,
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "include": ["src/**/*"]
}
```

`tsconfig.base.json` at the root with shared options (`strict`, `target`, `moduleResolution`, etc.).

### Typical development flow

Bring up everything with one command:

```bash
pnpm dev
```

Backend comes up on `localhost:3001`, frontend on `localhost:3000`. You change `packages/types/src/entry.ts` and TypeScript in `apps/web` already knows about the new type immediately, no restart.

Add a dependency to a specific app:

```bash
pnpm --filter @waypoint/api add express-rate-limit
pnpm --filter @waypoint/web add lucide-react
```

Add a dependency at the root (shared dev tool):

```bash
pnpm add -D -w prettier-plugin-tailwindcss
```

`-w` means "workspace root".

### CI (GitHub Actions)

`.github/workflows/ci.yml`:

```yaml
name: CI
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 9
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: "pnpm"
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm typecheck
      - run: pnpm test
```

No incremental cache (the limitation of plain pnpm), but with `actions/setup-node` caching `~/.pnpm-store` the install stays fast.

### Deploy (important note)

If you ever deploy via Vercel, configure the project pointing `rootDirectory` to `apps/web` and `installCommand` to `pnpm install --frozen-lockfile` running at the root. Vercel has a native "pnpm monorepo" preset, it works well.

The NestJS backend doesn't go on Vercel (not serverless-friendly without adaptation). Railway, Fly.io or Render, with a Docker build that runs `pnpm --filter @waypoint/api... build`, works without drama.
