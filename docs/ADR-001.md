# ADR-001: Polymorphic model for the Entry entity

**Status:** proposed
**Date:** 2026-07-07
**Context:** define the data structure of Waypoint's core entity

## Context

Entry is the polymorphic entity that represents anything captured through Quick Capture. There are 8 subtypes with partially overlapping fields:

| Subtype            | Specific fields                                                  |
| ------------------ | ---------------------------------------------------------------- |
| Learning           | source, related_context                                          |
| Achievement        | achievement_type, impact_type, momento_id                        |
| Question           | status (open/validate/answered), answer, answered_at, momento_id |
| Task               | due_date, category, priority, is_done, completed_at              |
| Link               | url, category, reviewed                                          |
| Study (log)        | resource_id, minutes_spent                                       |
| Technical decision | project_id, tradeoffs, outcome                                   |
| Feedback           | source, feedback_type                                            |

They all share: id, user_id, title, body, tags, created_at, updated_at, type.

There are three classic patterns for modeling this in Postgres, plus a hybrid that usually wins in practice.

## Options considered

### Option A: Single Table Inheritance (one big table)

A single `entries` table with every possible column, most of them nullable. A `type` column says which subtype it is.

**Pros:** trivial polymorphic queries (SELECT \* FROM entries WHERE user_id = X). No joins. Simple migration up front.

**Cons:** ugly table with 20+ columns, nearly all nullable. Nothing stops a Link from accidentally having due_date set. Per-subtype indexes become expensive because they cover irrelevant rows. Teaches almost nothing interesting about SQL.

**Verdict:** rejected. Scales poorly and adds no learning value.

### Option B: Table-Per-Type (base + one table per subtype)

A base `entries` table with the common fields, and a specific table per subtype (`tasks`, `questions`, `achievements`, etc.) with a 1-1 FK to `entries.id`.

```
entries (id, user_id, type, title, body, tags, created_at, updated_at)
├── tasks (entry_id FK, due_date, category, priority, is_done, completed_at)
├── questions (entry_id FK, status, answer, answered_at, momento_id)
├── achievements (entry_id FK, achievement_type, impact_type, momento_id)
├── links (entry_id FK, url, category, reviewed)
├── learnings (entry_id FK, source, related_context)
├── study_logs (entry_id FK, resource_id, minutes_spent)
├── decisions (entry_id FK, project_id, tradeoffs, outcome)
└── feedbacks (entry_id FK, source, feedback_type)
```

**Pros:** strong typing at the database level. Per-subtype constraints and indexes. Isolated per-subtype migrations. Teaches real joins and grown-up relational modeling.

**Cons:** 9 tables to maintain. A polymorphic query ("give me everything from this week") becomes a LEFT JOIN across 8 tables. Prisma supports it but not elegantly. A migration for every field change in any subtype.

**Verdict:** technically correct and rich didactically, but a high maintenance cost for a solo 2h/day project. If you jump straight here in Sprint 1, you'll spend all of Sprint 2 complaining about the polymorphic queries.

### Option C: Pure JSONB

A single `entries` table with a `data JSONB` column that carries everything subtype-specific. Shape validation via Zod in the application.

```
entries (id, user_id, type, title, body, tags, data JSONB, created_at, updated_at)
```

**Pros:** one table. Adding a field to any subtype is a code change, not a migration. Trivial polymorphic queries.

**Cons:** the database protects nothing. A bug in the app can save a Task with no due_date and nobody notices. Indexing a field inside JSONB requires an expression index or GIN, which is fiddlier to get right. It doesn't teach you Postgres, it teaches you to avoid Postgres.

**Verdict:** fast to start, but you're building this precisely to learn backend. Pure JSONB makes the SQL disappear.

### Option D (recommended): Evolutionary hybrid

Start with base + JSONB (option C), and **promote subtypes to their own table (option B) as they gain weight**.

Initial structure:

```
entries (
  id, user_id, type, title, body,
  tags text[], data jsonb,
  created_at, updated_at
)
```

Promotion rule: a subtype becomes its own table when any of these happens:

1. You need more than two indexes on its fields
2. You have a complex query involving aggregation (`SUM`, `COUNT`, `GROUP BY`)
3. You notice Zod validation isn't enough and you want a database constraint
4. The subtype has an FK relation to another entity you want to query from both sides

Applying this rule to the 8 subtypes today, **two are born as their own tables** because they are the interactive core of the app:

- **`tasks`**: filtering by is_done + due_date + priority is the main query of the Today widget. It runs every time you open the dashboard. It deserves a composite index.
- **`questions`**: filtering by status = 'open' is the query of the Open Questions widget. Also a dashboard hit.

The other six are born in JSONB and can be promoted later:

- Achievement: can be promoted once you start grouping by impact/type for the Brag Document
- Study log: can be promoted once you start summing minutes per trail
- Decision: can be promoted if its link to Projects gets queried from both sides
- Learning, Link, Feedback: probably stay in JSONB forever — they're more catalog than domain

## Decision

Option D. Start hybrid, with `tasks` and `questions` already as their own tables in Sprint 1, and the rest in JSONB. Migration to a dedicated table happens per sprint as subtypes gain weight.

## Consequences

**Positive:**

- Gradual learning curve: you touch JSONB, GIN indexes, expression indexes AND 1-1 relations, polymorphic joins, non-trivial migrations. It covers a lot of Postgres without all at once.
- Tiny initial schema: 3 tables (`entries`, `tasks`, `questions`). You ship Sprint 1 without suffering.
- Future promotions become legitimate learning exercises ("how to migrate data from JSONB to a dedicated table without downtime"), the kind of thing a real senior backend engineer does.

**Negative:**

- Zod schemas become mandatory in the shared `packages/types` package from day one, otherwise the JSONB turns into a dumping ground. This is not optional.
- A polymorphic query ("give me the last 20 Entries of any type") takes a LEFT JOIN to `tasks` and `questions`. Acceptable given the expected volume (personal use, dozens of rows per day).
- You need the discipline to promote subtypes when the promotion rule fires. If you ignore it, JSONB grows and becomes debt.

**Neutral:**

- Prisma models this well. Base + subtypes are just optional 1-1 relations. JSONB is a `Json` type and you refine it with Zod. No need for discriminated unions in the ORM.

## Implementation details

Initial Prisma schema (sketch):

```prisma
enum EntryType {
  LEARNING
  ACHIEVEMENT
  QUESTION
  TASK
  LINK
  STUDY_LOG
  DECISION
  FEEDBACK
}

model Entry {
  id        String   @id @default(cuid())
  userId    String
  type      EntryType
  title     String
  body      String?
  tags      String[]
  data      Json?     // used by subtypes not yet promoted
  createdAt DateTime  @default(now())
  updatedAt DateTime  @updatedAt

  user      User      @relation(fields: [userId], references: [id])
  task      Task?
  question  Question?

  @@index([userId, type, createdAt(sort: Desc)])
  @@index([userId, createdAt(sort: Desc)])
}

model Task {
  entryId     String   @id
  dueDate     DateTime?
  category    String
  priority    Int      @default(2)
  isDone      Boolean  @default(false)
  completedAt DateTime?

  entry       Entry    @relation(fields: [entryId], references: [id], onDelete: Cascade)

  @@index([isDone, dueDate])
}

model Question {
  entryId     String   @id
  status      String   // 'open' | 'validate' | 'answered'
  answer      String?
  answeredAt  DateTime?
  momentoId   String?

  entry       Entry    @relation(fields: [entryId], references: [id], onDelete: Cascade)

  @@index([status])
}
```

> Note: this Prisma sketch is superseded by ADR-002, which chose Drizzle as the ORM. It is kept here as the original record of the decision.

Shared Zod schemas in `packages/types/entry.ts`:

```typescript
export const LearningDataSchema = z.object({
  source: z.string().optional(),
  relatedContext: z.string().optional(),
});

export const LinkDataSchema = z.object({
  url: z.string().url(),
  category: z.string().optional(),
  reviewed: z.boolean().default(false),
});

// ...one per JSONB subtype

export const CreateEntryInput = z.discriminatedUnion("type", [
  z.object({
    type: z.literal("LEARNING"),
    title: z.string(),
    body: z.string().optional(),
    tags: z.array(z.string()),
    data: LearningDataSchema,
  }),
  z.object({
    type: z.literal("LINK"),
    title: z.string(),
    body: z.string().optional(),
    tags: z.array(z.string()),
    data: LinkDataSchema,
  }),
  // ...
  z.object({
    type: z.literal("TASK"),
    title: z.string(),
    body: z.string().optional(),
    tags: z.array(z.string()),
    task: TaskInputSchema,
  }),
  z.object({
    type: z.literal("QUESTION"),
    title: z.string(),
    body: z.string().optional(),
    tags: z.array(z.string()),
    question: QuestionInputSchema,
  }),
]);
```

Full-text search: create a generated `tsv` column on `entries` with `to_tsvector('portuguese', title || ' ' || coalesce(body, ''))` and a GIN index. It covers 90% of searches. To search inside the subtype-specific JSONB, add an expression index when you need it. (The `'portuguese'` text-search config matches the product's content language.)
