# ADR-002: ORM choice for the NestJS backend

**Status:** proposed
**Date:** 2026-07-07
**Context:** define the data access layer in NestJS + Postgres
**Supersedes:** the Prisma schema sketch from ADR-001, which was a placeholder

## Context

Waypoint's backend is NestJS + Postgres 16. It needs to support:

- The hybrid model from ADR-001 (base `entries` + promoted `tasks`/`questions` subtypes, the rest in JSONB)
- Full-text search in Postgres via tsvector + GIN
- Shared Zod schemas in `packages/types` to validate JSONB
- Git-trackable migrations
- Good DX for a nightly side project (2h/day, no patience for a complicated ORM)

An important secondary goal: you want to **learn SQL/Postgres deeply**. That becomes a decision criterion, not just a footnote. An ORM that abstracts SQL too much takes away what you want to practice.

## Options considered

### Option A: Prisma

The modern default for Node.js. Schema in its own DSL (`schema.prisma`), generated TypeScript client, Prisma Studio for exploring data visually.

**Pros:**

- Excellent DX, strong autocomplete, clear error messages
- Prisma Studio (visual database UI) is great for a visual person
- Declarative migrations (change the schema, run `prisma migrate dev`)
- World-class reference documentation
- Well-established NestJS ecosystem (official guides)

**Cons:**

- Abstracts a lot of the SQL. For complex queries you fall back to `$queryRaw`, which breaks the experience
- Schema in a non-TypeScript DSL. You write `.prisma`, not `.ts`
- Mandatory code generation (`prisma generate` every time you touch the schema)
- Full-text search and GIN indexes have to be added via raw SQL in migrations, somewhat outside the declarative flow
- For the goal of learning Postgres, it tends to hide what you want to see

### Option B: TypeORM

The historical ORM of the NestJS ecosystem. Entities as TypeScript classes with decorators.

**Pros:**

- Older and more battle-tested NestJS integration
- `nest g resource` generates a full CRUD including entity, service, controller and DTO
- Decorators match the style of the rest of NestJS
- Supports both Active Record and Data Mapper

**Cons:**

- Lukewarm maintenance in recent years. Several known bugs that linger
- Typing has weak spots, especially in relations and complex queries
- Heavy decorators clutter the entities
- Migrations less fluid than Prisma or Drizzle
- The community is moving to Prisma and Drizzle

### Option C: Drizzle

SQL-first. You write the schema in plain TypeScript using functions that mirror SQL. Typed query builder. No code generation.

**Pros:**

- The schema is plain TypeScript, no separate DSL
- A query builder designed to look like SQL. You still see what the database will execute
- Migrations in native SQL, versioned in git. You read and understand each one
- First-class JSONB support with `$type<>()` that types the content
- Full-text search, GIN indexes, expression indexes: all directly accessible
- Drizzle Studio exists (less powerful than Prisma Studio, but covers the essentials)
- **You already use it in FinSight AI**. That removes one new variable while you're learning NestJS at the same time

**Cons:**

- Smaller NestJS ecosystem. No `nest g resource` equivalent. You wire up injection manually
- Good docs but less dense than Prisma
- Fewer "official guides" for production patterns. You'll improvise more

### Option D: Kysely (pure query builder)

A typed query builder without an ORM. Migrations managed separately.

**Pros:** the thinnest, closest to SQL. Excellent typing.

**Cons:** not an ORM, you build the repository layer by hand. For a solo project at night, it's overhead with no clear payoff.

**Verdict:** interesting but not for now. Noted as an option for a future performance-focused project.

## Decision

**Drizzle.**

The deciding weight is alignment with the two goals you declared:

1. **Learn Postgres deeply.** Drizzle is the only option that keeps you in constant contact with real SQL. You see the join, you write the GIN index in the migration, you understand what the generated tsvector column does. Prisma would solve that for you and you'd learn Prisma, not Postgres.

2. **Reduce the parallel learning surface.** You're already facing NestJS for the first time in your own use. Adding Prisma alongside means two new tools at once. Drizzle is the only one where the syntax is already in your memory from FinSight AI. That frees mental energy to focus on NestJS (guards, interceptors, pipes, providers), which is what you really want to practice.

The trade-off is real: you give up Prisma Studio (good for a visual person) and TypeORM's automatic CRUD generation. Compensations:

- Drizzle Studio (`drizzle-kit studio`) covers most of what you need visually
- The absence of `nest g resource` is a chance to learn the NestJS module structure by hand, which is good didactically

## Consequences

**Positive:**

- Schema, migrations and queries in plain TypeScript. A single vocabulary.
- You stay in contact with SQL. Portuguese full-text search, GIN on JSONB, expression indexes are all readable in your code.
- You reuse the fluency you already have from FinSight AI.
- Zero code generation. Less friction in the dev loop.

**Negative:**

- You wire up the NestJS integration by hand. You'll create a global `DrizzleModule` that exposes the client via injection. Two hours of setup in Sprint 0.
- No Prisma Studio. If you miss it badly, run `drizzle-kit studio` or use TablePlus/Beekeeper Studio as a Postgres client.
- If one day you want to move to Prisma, the cost isn't trivial (schema DSL, code generation). But that's a hypothetical problem.

**Neutral:**

- Zod remains the validation at the edges (controllers) and in the JSONB `$type<>()`. Nothing changes in ADR-001 here.
- Migrations become SQL in the `drizzle/` folder. They can be reviewed in a PR as code.

### The ADR-001 schema redone in Drizzle

Replaces the Prisma example from ADR-001. This is the official one:

```typescript
// apps/api/src/db/schema/entries.ts
import {
  pgTable,
  text,
  timestamp,
  jsonb,
  index,
  pgEnum,
} from "drizzle-orm/pg-core";
import { createId } from "@paralleldrive/cuid2";
import { users } from "./users";

export const entryTypeEnum = pgEnum("entry_type", [
  "learning",
  "achievement",
  "question",
  "task",
  "link",
  "study_log",
  "decision",
  "feedback",
]);

// JSONB payload type per subtype, validated by Zod in the controller
export type EntryData =
  | { source?: string; relatedContext?: string } // learning
  | { url: string; category?: string; reviewed: boolean } // link
  | { achievementType: string; impactType: string; momentoId?: string } // achievement
  | { resourceId: string; minutesSpent: number } // study_log
  | { projectId?: string; tradeoffs: string; outcome?: string } // decision
  | { source: string; feedbackType: "positive" | "constructive" }; // feedback

export const entries = pgTable(
  "entries",
  {
    id: text("id")
      .primaryKey()
      .$defaultFn(() => createId()),
    userId: text("user_id")
      .notNull()
      .references(() => users.id, { onDelete: "cascade" }),
    type: entryTypeEnum("type").notNull(),
    title: text("title").notNull(),
    body: text("body"),
    tags: text("tags").array().notNull().default([]),
    data: jsonb("data").$type<EntryData | null>(),
    createdAt: timestamp("created_at").defaultNow().notNull(),
    updatedAt: timestamp("updated_at").defaultNow().notNull(),
  },
  (t) => ({
    userTypeDate: index("idx_entries_user_type_date").on(
      t.userId,
      t.type,
      t.createdAt,
    ),
    userDate: index("idx_entries_user_date").on(t.userId, t.createdAt),
  }),
);
```

```typescript

import { pgTable, text, timestamp, index } from "drizzle-orm/pg-core";
import { entries } from "./entries";

export const questions = pgTable(
  "questions",
  {
    entryId: text("entry_id")
      .primaryKey()
      .references(() => entries.id, { onDelete: "cascade" }),
```

### Full-text search: generated column + GIN index

This is a manual SQL migration, not generated by Drizzle. It lives in `drizzle/000X_fts.sql`:

```sql
ALTER TABLE entries
  ADD COLUMN tsv tsvector
  GENERATED ALWAYS AS (
    to_tsvector('portuguese', coalesce(title, '') || ' ' || coalesce(body, ''))
  ) STORED;

CREATE INDEX idx_entries_tsv ON entries USING GIN (tsv);
```

Query in the service:

```typescript
import { sql } from 'drizzle-orm';

async search(userId: string, query: string) {
  return this.db
    .select()
    .from(entries)
    .where(sql`user_id = ${userId} AND tsv @@ plainto_tsquery('portuguese', ${query})`)
    .orderBy(sql`ts_rank(tsv, plainto_tsquery('portuguese', ${query})) DESC`)
    .limit(20);
}
```

### DrizzleModule in NestJS (skeleton)

```typescript
// apps/api/src/db/drizzle.module.ts
import { Global, Module } from "@nestjs/common";
import { drizzle } from "drizzle-orm/node-postgres";
import { Pool } from "pg";
import * as schema from "./schema";

export const DRIZZLE = Symbol("DRIZZLE");

@Global()
@Module({
  providers: [
    {
      provide: DRIZZLE,
      useFactory: () => {
        const pool = new Pool({ connectionString: process.env.DATABASE_URL });
        return drizzle(pool, { schema });
      },
    },
  ],
  exports: [DRIZZLE],
})
export class DrizzleModule {}
```

Usage in a service:

```typescript
@Injectable()
export class EntriesService {
  constructor(@Inject(DRIZZLE) private db: NodePgDatabase<typeof schema>) {}

  async listByUser(userId: string) {
    return this.db.select().from(entries).where(eq(entries.userId, userId));
  }
}
```
